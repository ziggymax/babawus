# Planning the next release

The purpose of this document is to have a place to capture ideas for the next release of Babawus and, in doing so, help in creating and maintaining a general plan for the future work on Babawus.

Some releases may represent so much work and/or complexity that a step-by-step sequence of interim non-released versions is needed to reach the stage where a new release can be made. These non-released versions are an important part of the release planning and hence also something that will be described in this document.

For the remainder of this document the word "version" is used for something that is not planned to be released, and the word "release" is used only for something that is intended for release.

Interim versions are numbered as semver pre-releases of the release they lead to, for example 1.0.0-alpha.1, 1.0.0-alpha.2, and so on. Each interim version is tagged on main, but gets no GitHub release.

When work on a version begins, its items become tasks (T-entries) in the task list.

## Next release of Babawus

This section always describes the next upcoming version/release of Babawus. Some of the ideas may be very specific, and some more speculative in nature. Task(s) created to deal with speculative ideas will be investigative rather than implementation-oriented.

### Administrative matters or other non-feature tasks

1. From 1.0.0 onwards, Babawus follows the rules of semantic versioning (major.minor.patch). The next release, 1.0.0, is the first stable release.
1. The following documents should be cleaned up and consolidated based on the current version and the experiences gathered up till now.
    - Concept
    - Requirements
    - Issues: split into Issues-Unsettled.md and Issues-Resolved.md, rather than one file that just grows endlessly. A new issue is born and given its number in Issues-Unsettled.md, and is later moved to Issues-Resolved.md, keeping its number. Issue numbers are unique and persistent, so history and cross-references are kept. References elsewhere say just "issue 132", without a file name, so they never go stale when an issue moves.
    - Tasks: split the same way into Tasks-Open.md and Tasks-Done.md. A task keeps its T-number when it moves, and references say just "T-063".
    - DevEnvSetup
    - ReleaseChecklist

### New features

To the extent possible the new features are listed by priority, from highest to lowest.

1. *Make it easy to add new languages*. Maintain the available languages as language files that:
    - are easy to find, enumerate and list
    - are easy to manage, e.g. have a format that makes it easy to add new language translations, including ones generated by machine or AI, which are treated like any other language file.

    Further decisions:
    - The language files are loaded at runtime, so a language can be added without a new build.
    - English is a language file like the others. If it is missing or broken, Babawus shows an error and stops.
    - A language file that is broken or incomplete (missing texts, wrong placeholders, syntax errors) is rejected: it is not offered in the Language menu, and the reason is written to the log.
    - The file format is not decided yet. The first task of the version is to investigate and choose it, against our needs: switching language at once without a restart, placeholders, and tool support (candidates include Fluent, gettext and TOML).
1. *Revisit the "power user concept"*. Many users will do all the work with Babawus themselves, i.e. both doing regular backups and advanced stuff (formatting drives, changing setups etc), so referring to some other non-existent "power user" may seem odd.
A better alternative would be to use a concept simply called "Advanced features". Every time the user chooses "Advanced" from the menu, a pop-up appears with a suitable warning about the dangers of using advanced features and two options: "Cancel" or "Continue". A non-technical user can then opt out, and the tech-savvy person can just continue. No text/wording in Babawus implies anything about how/where to get help with advanced features or diagnosing problems. This covers:
    - every text that mentions a poweruser, or someone who looks after the computer
    - the description in the .deb package
    - the German texts, which use "Betreuer" for the poweruser (issue 91)
    - an audit of all texts, in every language, for any other such wording.

    The Ext4 text that suggests asking an administrator stays, as it refers to the system administrator (sudo), not the poweruser.

    A small built-in "Help" will be added to the menu that very briefly explains the what/why/how of using Babawus. It opens in a window of its own that isn't modal, so it can stay open while Babawus is used.

## Future releases

This section captures ideas for some future, unspecified releases of Babawus. As time and versions progress some of these ideas will migrate to the "Next release of Babawus" section, some will be deleted and some may live here for a long time.

To the extent possible the new features are listed by priority, from highest to lowest.

1. *A runnable release script(?)*. Investigate the possibility of automating releases to the maximum by maintaining the release procedure as some kind of runnable script. Anything that can be done without human intervention should be done automatically, where human intervention is needed the script should prompt the person responsible for doing the release with step-by-step actions to perform (and, where the person must report some result back, provide simple fillable forms).
1. *Restore file(s) window*. A user should be able to open a window showing files/folders (shown in much the same way that the what-backup pane does) and select one or more specific files to restore. When a file has earlier versions stored, the user should (also) be able to see and pick specific versions.
1. *Prepare for other platforms*. Future versions of Babawus should be able to work with the platforms listed below. For the next release the task is to investigate the need for code restructuring/refactoring to accommodate this overarching goal.
Any actual refactoring will be done in a later version - it will probably be a good idea to create some non-released interim versions to achieve these goals.
    - Ubuntu and other .deb using platforms (this is a short term goal). What differs from Mint is not known yet; finding out is part of the investigation.
    - Windows (a longer term goal)
